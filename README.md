# LCF Regulatory Data Intelligence

A small, source-linked **Regulatory Data Intelligence** workspace for tracing regulatory obligations into technical data impacts. The product model is generic and multi-regulator: it is not a regulator-specific dashboard, a CADOC product, or an official filing channel.

> **DEMO DATA.** Internal systems, datasets, mappings, test rows, generated artifacts and pipeline runs in this repository are synthetic. Curated regulatory excerpts are separate from those fixtures. Nothing generated by this application is transmitted to a regulator or validated by an official regulator validator.

## Run locally

**Requirements:** Node.js `>=22.5.0` (tested with Node `v22.22.3`). The implementation uses the experimental built-in `node:sqlite`; no npm packages are required.

```bash
npm test
npm start
```

Open <http://localhost:3000>. The server binds to `0.0.0.0` for hosted previews. The first start creates `data/regtech.sqlite`, applies the numbered SQL migrations in order, and seeds the database. The local SQLite file, write-ahead log and generated demo artifacts are ignored by Git.

Optional development mode:

```bash
npm run dev
```

There is no separate frontend build step; the interface is static HTML, CSS and browser JavaScript served by the Node HTTP server.

## Product flow

The common reference path is:

```text
Official source / version / snapshot
  → regulation
  → regulatory_obligation
  → requirements + deadlines + document
  → schema version + sourced field inventory
  → canonical concept + internal data field + mapping
  → pipeline dependency + DQ rule
  → submission artifact / local validation
  → control + evidence + append-only audit event
```

The SQLite migration models that path alongside source snapshots, extraction candidates, regulatory changes and technical impacts, internal systems/datasets, pipeline and DQ runs, validation results, errors, and a cross-regulator reference-case library. Obligation-to-data and data-to-regulation navigation is derived from persisted joins rather than regulator-specific page logic. Mapping transforms use a small explicit allowlist (`IDENTITY`, `LEFT_PAD`, `DECIMAL`, date formats and uppercase); arbitrary SQL/JavaScript strings are never evaluated, and unknown transforms fail closed.

### Impact rules

`src/engines/impact-engine.js` maps typed change classes to a deterministic set of technical impact categories, points, rationales and recommended actions. Its `LOW`–`CRITICAL` result is an engineering triage classification. Separately, the obligation inventory footprint score uses stored format, cadence, fields and mappings; it is explicitly a structural heuristic—not legal materiality, regulatory severity, or an applicability decision.

### Source provenance and ingestion

Each curated source record retains authority, source URL, source type, publication/version metadata, stored excerpt and hash scope. Seed hashes are `CURATED_EXCERPT_SHA256`: they hash the local curated text, **not the original PDF/HTML/XLS bytes**. Source URLs are preserved alongside the excerpt and its citation.

The optional collector in `src/engines/ingestion.js` accepts HTTPS URLs only on an official-host allowlist (`gov.br`, `bcb.gov.br`, `cvm.gov.br`, `planalto.gov.br`, `in.gov.br`), re-checks each redirect target, limits response size to 12 MiB, stores immutable response bytes and a raw-response SHA-256, and logs failures. Network access is environment-dependent. A source hash change creates a review item; it does not claim a semantic rule change. Text/schema extraction creates low-confidence human-review candidates and never automatically publishes obligations or fields. PDFs and unsupported binary types may remain `UNSTRUCTURED`.

The seed has **zero raw snapshots**. Running tests against a mocked fetcher verifies the collector path but does not create a real snapshot of an official website.

## Integrated regulators and key official references

The URLs below are stored in the source registry with the authority, source type and available version/date metadata. Curated excerpts in `src/seed.js` are deliberately narrower than their original publications; consult the official document before implementing a production rule.

### Banco Central do Brasil (BCB)

- Documento 3040 catalog: <https://www.bcb.gov.br/estabilidadefinanceira/scrdoc3040>
- Official 3040 layout XLS: <https://www.bcb.gov.br/content/estabilidadefinanceira/Leiaute_de_documentos/scrdoc3040/SCR3040_Leiaute.xls>
- 3040 filling instructions: <https://www.bcb.gov.br/content/estabilidadefinanceira/Leiaute_de_documentos/scrdoc3040/SCR_InstrucoesDePreenchimento_Doc3040.pdf>
- Published non-accounting/Cosif deadline calendar: <https://www.bcb.gov.br/content/estabilidadefinanceira/supervisao/Prazos_Nao_contabeis_Cosif.pdf>
- Documento 4111 instructions: <https://www.bcb.gov.br/content/estabilidadefinanceira/Documents/Leiaute_de_documentos/saldosDiariosInstrucoesPreenchimentoV2.pdf>

The curated 4111 change event records the official manual history entry dated 7 May 2026 that changed the CNPJ representation to eight alphanumeric characters; the prior full source file was not captured. The published 3040 calendar due date for reference period 2026-09 is 14 October 2026. The 4111 calendar row for data-base 2 October 2026 is derived from the manual's third-business-day rule and the limited local national-holiday set; it is not a separately published calendar date.

### Comissão de Valores Mobiliários (CVM)

- Consolidated Resolução CVM 80: <https://conteudo.cvm.gov.br/export/sites/cvm/legislacao/resolucoes/anexos/001/resol080consolid.pdf>

The seed structures the annual Formulário de Referência obligation (deadline is up to five months after each issuer's fiscal year-end) and the Formulário Cadastral change/annual-confirmation rule (seven business days after a change; annual confirmation by 31 May). Filing forms are represented as electronic forms; a full technical payload schema is not asserted.

### Superintendência de Seguros Privados (SUSEP)

- Official data-submission responsibility catalog: <https://www.gov.br/susep/pt-br/servicos/mercado/enviar-dados/areas-responsaveis-pelos-dados>
- Manual de Orientação para Envio de Dados, version 02/2026: <https://www.gov.br/susep/pt-br/servicos/mercado/enviar-dados/arquivos/manual_orientacao_envio_dados_Mar2026.pdf/@@display-file/file>
- Open Insurance Manual de Escopo de Dados e Serviços, version 6.7: <https://www.gov.br/susep/pt-br/assuntos/open-insurance/arquivos/copy_of_Manual_de_Escopo_de_Dados_e_Servicos_v6.7.pdf/@@display-file/file>

The model keeps monthly FIP (`.MDB`) separate from annual R_COMP/S_COMP (`.DBF` in `.ZIP`, due 31 March under the cited 02/2026 manual). Eighteen R_COMP table fields are catalogued; a DBF writer is not implemented. Open Insurance is represented as an API-sharing obligation and versioned scope manual. The v6.7 Tabela 51 domain addition is linked to a change event, but its complete endpoint schema, JSON/OpenAPI contract and field inventory remain uncaptured and are explicitly `UNSTRUCTURED`.

### Autoridade Nacional de Proteção de Dados (ANPD)

- Current incident-notification guidance: <https://www.gov.br/anpd/pt-br/canais_atendimento/agente-de-tratamento/comunicado-de-incidente-de-seguranca-cis>
- Resolução CD/ANPD 15/2024 (Diário Oficial da União): <https://www.in.gov.br/en/web/dou/-/resolucao-cd/anpd-n-15-de-24-de-abril-de-2024-556243024>

The three-business-day notice is conditional: the incident must be confirmed, involve personal data subject to LGPD, and be capable of causing relevant risk or damage, subject to a specific statutory deadline. The electronic SEI!ANPD process is catalogued; its technical payload schema is not invented.

### Conselho de Controle de Atividades Financeiras (COAF)

- COAF FAQ: <https://www.gov.br/coaf/pt-br/acesso-a-informacao/perguntas-frequentes-3>
- Lei 9.613/1998: <https://www.planalto.gov.br/ccivil_03/leis/l9613.htm>

Customer identification, records and communications are represented as separate generic obligations. The FAQ's five-year minimum record-retention note is sourced; reporting populations and deadlines remain segment-specific. The application intentionally does **not** encode a universal COAF reporting deadline.

### Receita Federal do Brasil (RFB)

- Manual de Orientação do Leiaute da DeCripto: <https://www.gov.br/receitafederal/pt-br/centrais-de-conteudo/publicacoes/manuais/manual-orientacao-leiaute-criptoativos/manual-de-orientacao-do-leiaute-da-decripto-v1.pdf>

The curated source identifies the manual's 1.01 version, pipe-delimited UTF-8 format and the new-model start date of 1 July 2026. Twenty-four selected fields from records 0000 and 0110 are inventoried. That is **not** a complete current DeCripto schema or file serializer; the full record inventory, complete schema and exact universal cadence/deadline are not claimed here.

## User interface modules

The browser UI is a responsive, information-dense workspace with:

- cross-regulator overview, global search, regulator pages and obligation inventory/detail;
- source-linked regulatory change feed, lexical norm comparison and version/field schema registry;
- obligation-to-data trace, reverse lineage, impact matrix, mapping studio and canonical catalog;
- executable DQ rules and row-level results against labeled synthetic fixtures;
- official deadline list and a separate form/list for internal planning targets;
- control library, evidence metadata register and audit trail;
- source collection/processing job history and retryable ingestion errors;
- generic adapter inventory, generated submission/artifact history, local-only validation, and reference cases.

### Generic submission adapters

`src/engines/submission-adapters.js` provides generic XML, CSV, JSON, fixed-width and pipe-delimited serializers with metadata-based local checks. Adapter support is not the same as regulator support. DBF/MDB writers, regulator transport/authentication, official validator integration, regulator acknowledgements and production credentials are not implemented. The only seeded runnable mapping/schema configuration is a clearly labeled BCB 4111 demonstration; it is a test case, not the product's architecture or a real submission. A local status of `READY` means **internal review only**.

## Limitations and next steps

This repository is an auditable prototype, not a production compliance platform. Important gaps are explicit:

- only curated excerpts are seeded; no original regulatory bytes or hashes are present yet (raw snapshot count 0);
- source-network access may fail in a restricted environment, and PDF/XLS/DBF/MDB parsing is incomplete;
- extracted obligations and fields require legal/domain review; no automated legal interpretation or entity applicability decision exists;
- several documents are partial or unstructured; no full OpenAPI/XSD or regulator-specific validator is claimed;
- only BCB 4111 has a configured runnable adapter; local XML checks are intentionally lightweight;
- default business-day holidays cover a small national date set and are not a complete regulator, bank, state or entity-specific calendar;
- no authentication, authorization, tenant isolation, secrets management, production database, queue, object store or external control integration is configured;
- the internal data estate, evidence artifacts and submission payloads are demo-only.

Reasonable next steps are to capture and retain official source bytes in an approved networked environment (with response URL, timestamps, MIME type and SHA-256), expand parser/schema coverage with human review, add entity-specific calendars and applicability ownership, implement regulator-tested adapters/validators, and add authentication and deployment controls before production data is introduced. PostgreSQL/FastAPI are not prerequisites for running this repository; the current no-dependency SQLite implementation reflects the available local runtime.
